# 조회·예약과 재시도 정책

작성일: 2026-09-12
상태: 15~30초 가변 간격과 10개 큐 보정 적용. 성공 또는 직접 중단까지 기본 연속 실행.

## 목적

조회 간격, 통신 오류의 재시도, 접근 제한 시 중단 및 중복 예약 방지 동작을 설명한다.
조회 횟수·실행 시간·HTTP 총량 상한은 기본적으로 없으며 옵션으로 지정할 수 있다.

현재 수치는 프로젝트의 자체 설정이다. 운영사의 허용 기준이나 실제 탐지 임계값으로
확인된 값은 아니며, 탐지 방지 효과도 검증하지 않았다. 이 문서는 로컬 구현과 기존
검증 기록을 근거로 작성한다.

## 현재 조회 정책

`train_cli.py`의 예매 메뉴와 `reservation.py`는 모두 `reservation_guard.py`를 사용한다.

| 항목 | 현재 동작 | 설계 의도 |
|---|---|---|
| 조회 간격 | 기본 15~30초, 입력 가능한 최솟값 15초, 예정 간격 10개를 큐로 관리 | 대기 시간에 변동을 주고 짧거나 긴 간격으로의 편중 보정 |
| 조회 횟수 | 기본 무제한, 옵션으로 양수 상한 지정 가능 | 성공까지 연속 조회 |
| 실행 시간 | 기본 무제한, Ctrl+C로 중단, 옵션으로 양수 상한 지정 가능 | 시간 경과만으로 종료하지 않음 |
| HTTP 요청 | 기본 무제한, 내부 요청 횟수 기록, 옵션으로 양수 상한 지정 가능 | 누적 요청 수만으로 종료하지 않음 |
| 통신 오류 | 연속 3회에서 종료, 첫째·둘째 오류 뒤 기본 120초·240초 대기 | 오류 중 반복 요청 완화 |
| 세션 재사용 | 같은 클라이언트 사용, 명시적인 세션 만료 시에만 1회 재로그인 | 불필요한 로그인 반복 억제 |
| 동시 실행 | 같은 프로젝트 폴더에서 조회·예약 작업 하나만 실행 | 중복 프로세스의 요청 중첩 방지 |
| 개별 HTTP 요청 | 최대 15초 타임아웃, 자동 리디렉션 비활성화 | 대기 시간과 숨은 추가 요청 제한 |

조회 간격은 한 번의 논리적 조회 처리가 끝난 뒤 다음 조회까지의 대기 시간이다.
조회 한 번에 여러 페이지를 요청할 수 있으며, 페이지별 HTTP 요청 사이에 별도의
가변 대기를 삽입하는 구조는 아니다. 로그인·인증·대기열·페이지 이동·예약 내역 확인도
HTTP 횟수에 포함된다. 상한을 별도로 지정하면 내부 요청까지 합산해 적용한다.

시간·HTTP 한도를 지정한 경우 요청을 보내기 전에 검사한다. 진행 중인 통신은 설정된 타임아웃까지
걸릴 수 있다. 통신 오류 대기는
`max(interval, min(max(60초, interval) × 2^연속오류수, 300초))`로 계산한다.
정상 간격의 최솟값을 낮춰도 기본 오류 대기는 120초·240초를 유지한다.

`--interval`, `--max-interval`, `--max-searches`, `--max-minutes`, `--max-requests`로
값을 지정할 수 있다. 세 가지 총량 옵션을 생략하면 각각 제한이 없으며, 명시한 값은
양수여야 한다. 내부적으로 제한 없음은 `None`으로 표현한다. 로그인 설정과 예약 내역
확인 메뉴의 별도 시간·HTTP 상한은 그대로 적용한다.
명령행 기본값과 메뉴 안내는 `Policy`의 기본값을 사용한다.
예매 메뉴에서도 최소·최대 조회 대기 시간을 입력할 수 있다.

KTX 조회는 페이지마다 시간 순서를 검증하고 열차·시간·좌석 조건을 확인한다.
예약 가능한 후보가 있는 페이지를 받으면 이후 페이지를 요청하지 않고 예약 단계로 넘어간다.
후보가 없으면 다음 페이지를 조회한다. 알림 모드도 잔여석 발견 페이지에서 종료한다.
기존 예약·승차권 확인은 탐색 전에 완료하며, 예약 결과 재확인 절차는 동일하게 적용한다.

## 10개 대기 큐와 편중 보정

기본 최소 대기는 15초, 최대 대기는 30초다.
현재 기본 범위에서 짧은 간격 또는 긴 간격이 여러 개 쌓이면
반대쪽 간격을 추가하도록 한다. 범위의 중간값인 22.5초를 보정 기준으로 사용한다.
이는 고정 주기나 매 10회 총 대기 시간을 보장하는 값이 아니다.

`IntervalQueue`는 실행마다 앞으로 사용할 간격 10개를 FIFO 큐에 유지한다.

1. 첫 간격은 전체 범위에서 균등 무작위 추출한다.
2. 초기 큐의 나머지 항목도 이미 들어 있는 간격의 평균을 보고 아래 보정 규칙으로 채운다.
3. 다음 조회를 기다릴 때 큐의 맨 앞 간격을 꺼낸다.
4. 남은 9개 평균이 중간값보다 작으면 상반부(기본 22.5~30초), 크면 하반부
   (기본 15~22.5초), 같으면 전체 범위에서 균등 무작위로 하나를 뽑아 뒤에 넣는다.
5. 꺼낸 시간만큼 기다린 뒤 다음 조회를 진행한다. 별도로 지정한 총 실행 시간이 먼저
   끝나거나 사용자가 Ctrl+C를 누르면 종료한다.

이미 정한 항목의 값과 순서는 바꾸지 않는다. 편중 보정은 큐 뒤에 추가하는 간격에
적용되므로 즉시 다음 간격을 뒤집거나 짧은 간격의 연속 출현을 완전히 금지하지 않는다.
하나를 꺼낸 뒤 추가하므로 큐의 크기는 항상 10개다. 최솟값·최댓값을 같게 지정하면
해당 고정 간격으로 동작한다.

통신 오류에 따른 대기는 별도로 계산하고 정상 대기 큐를 소비하지 않는다.
자동예약·알림 실행의 초기 로그인, 세션 재로그인, 시작 전 예약·승차권 확인에도
같은 통신 오류 대기와 연속 3회 한도를 적용한다. 실패한 단계와 원인 예외 종류를
표시·기록하며 인증 거절·접근 제한·알 수 없는 오류에는 이 재시도를 적용하지 않는다.
이 준비 단계 재시도는 예약 요청을 재전송하지 않으며 시간·HTTP 한도를 계속 적용한다.
첫 조회는 바로 실행한다. 좌석 발견 후의 예약 전송을 지연시키거나 여러 예약을 큐에
넣지 않는다. 이 큐는 논리적 잔여석 조회 사이에만 적용한다.

기본 실행에는 조회 상한이 없으므로 큐 뒤에 보충한 항목까지 계속 순환해 사용한다.
예약에 성공하면 종료하며, 알림 모드는 잔여석 발견 시 종료한다. 기존 예약이 있으면 중단하며,
예약 결과가 불명확하면 내역 확인 중 추가 예약을 보내지 않는다. 연속 통신 오류 3회, 재인증 한도 초과,
접근 제한 및 알 수 없는 오류도 기존 중단 조건으로 유지한다.

## 인증과 접근 제한 처리

- KTX는 `MobileKorail`에서 `KorailConfig(enable_dynapath=True)`를 사용한다.
  인증 호환성을 위한 라이브러리 설정이며, 탐지 방지 효과를 보장하는 근거는 아니다.
- 기존 기록에는 구형 클라이언트의 `MACRO ERROR`와 새 클라이언트의 로그인·조회 성공이
  남아 있다. 이 결과만으로 반복 조회의 탐지 조건을 판정하지 않는다.
- `MACRO ERROR`, 매크로·차단·CAPTCHA 등 제한 신호, DynaPath 오류, 대기열 거절,
  추가 인증 요구는 중단 대상으로 처리한다.
- HTTP 401·403·429 및 3xx 응답은 해당 실행의 추가 HTTP 요청을 중단한다.
- 접근 제한을 일반 통신 오류로 분류해 재시도하지 않는다. 세션 만료에 대한 1회
  재로그인은 접근 제한 후 재로그인과 구분한다.
- 프로젝트 코드에는 큐 기반 조회 간격 무작위화가 구현되어 있다. 주기적 세션 교체는
  구현하지 않았다. 가변 간격이 매크로 탐지를 방지한다고 보장하지 않는다.

## 예약과 기록

예약 전 기존 예약·승차권과 로컬 시도 기록을 확인하고, 예약 호출 반환 또는 예외 발생 후 상태를 저장한다.
예약 응답이 불명확하면 예약·승차권 내역을 확인한다. 정상 조회 간격을 두고 두 차례 연속
해당 열차가 없으면 `retryable`로 기록한 뒤 잔여석 조회와 예약을 다시 시도한다.
내역 조회 오류가 나면 부재 확인 횟수를 초기화하고 대기 후 재확인한다. 예약이 확인되면
성공 처리한다. 재시작 시 남아 있는 `uncertain` 기록에도 같은 확인 절차를 적용한다.
내역 확인 중에는 추가 예약을 보내지 않으며 접근 제한·시간·HTTP 한도·수동 중단은 유지한다.
내역 반영 지연 가능성이 있어 두 차례 부재 확인이 중복 예약을 완전히 배제하지는 않는다.

감사 로그에는 시각·요청 횟수·상태 코드·오류 종류·처리 상태 등을 남긴다.
자격 증명, 토큰, 요청 URL, 원문 응답은 기록하지 않는다. 텔레그램 알림은 철도 HTTP
한도와 별도로 예약 성공 시 한 번 전송한다.

## 후속 조회 정책 변경 기준

1. 조회 기회를 늘릴 때는 조회 횟수·실행 시간과 조회 빈도를 나누어 검토한다.
   횟수와 시간을 늘리는 변경도 누적 요청량을 늘리므로 함께 산정한다.
2. 선택적으로 상한을 정할 때는 논리적 조회 횟수뿐 아니라 페이지 수, 로그인,
   예약 전후 내역 확인에 필요한 HTTP 요청을 포함한다.
3. 간격 단축이 필요하면 변경 이유와 예상 요청량을 명시한다. 기존 60초를 포함한 어떤
   간격도 검증된 탐지 방지 기준으로 취급하지 않는다.
4. 접근 제한 시 중단, 통신 오류 시 대기 증가, 세션 재사용, 단일 실행, 중복 예약
   방지 동작을 후속 변경에서도 유지한다.
5. 변경한 기본값은 `Policy`, 명령행 인자, 메뉴 안내, README에 일관되게 반영한다.
   요청 상한·대기·중단 동작은 기존 오프라인 테스트로 검증한다.

현재 기본값은 15~30초이며 조회 횟수·실행 시간·HTTP 총량 제한은 없다.
